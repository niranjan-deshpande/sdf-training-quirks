# 02: $/arm of the current Qwen3-14B recipe on A100 80GB / RTX PRO 6000 vs H100 (agent 02, GPU)

Status: **no s/step measured.** The one pod I launched, an A100 80GB PCIe on Community at $1.19/h, never got
through setup inside the 20-minute window. That failure is itself a measured result about cheap Community
hosts (see below). The s/step and $/arm numbers below are **estimates**, and the plan at the end measures
them for about $1.2.

## TL;DR
- **Measured (setup, not training):** The Community A100 PCIe host (pod jlznyuwjbnd1hx) was heavily
  oversubscribed, with a container-visible load average of ~665. The Qwen3-14B download took **3 min 46 s**
  (~130 MB/s), against 15 s on the earlier H100. The `uv pip install -e .[gpu]` step **stalled for more than
  9 minutes**, with the uv cache stuck at ~6 GB, against 13 s before. I deleted the pod at 9.2 min.
  Spend: ~$0.18. On cheap Community hosts, setup time and the risk of a stall can cancel the hourly
  saving unless there is a setup-speed gate or a prebuilt image.
- **Estimate (training only):** The A100 PCIe should run 2.2–3.0× slower than an H100 SXM, i.e.
  5.3–7.2 s/step. That gives **$1.28–1.74 per 730-step arm**, against **$1.31 on H100 Community ($2.69/h)**
  and **$1.94 on H100 Secure ($3.99/h)**. So it is roughly break-even with H100 Community and about 10–35%
  cheaper than H100 Secure. The RTX PRO 6000 at $1.69/h is estimated at 4.1–5.3 s/step, or $1.40–1.81 per
  arm. That is no better than the A100 on paper, unless its 96 GB allows gradient checkpointing to be
  turned off at per-device batch 16 (not measured).
- **Recommendation:** Do not switch hardware on these estimates. Run the 2-pod benchmark in the plan below
  (~$1.2 total), with a setup gate. The decision rule: the A100 wins over H100 Community only if it
  measures **< 5.4 s/step**, and over H100 Secure if **< 8.0 s/step**. The PRO 6000 must measure
  **< 3.8 / < 5.7 s/step** respectively.

## Findings

### F1. Community A100 setup can stall: per-arm cost then depends on host quality, not on the GPU (measured, n=1 host)
- **What happened:** pod created 22:55:00Z, SSH up after 2 s, `pod_setup.sh` started. The model download
  finished at ~3:46. The venv install (`uv pip install -e .[gpu]`, ~12 GB of torch/vLLM wheels) was still
  running at 9 min, with the cache growing 6.0 → 6.1 GB over 2 minutes. Container load average was 665–669.
  The run never started.
- **Why it matters for $/arm:** A 10-minute setup at $1.19/h is only $0.20. A stalled pod, though, wastes
  the whole session and the operator's time. The same setup took ~30 s on the H100 (HANDOFF §0).
- **Mitigations (cheap):**
  1. Add a setup gate to launch_pod.sh: if `/root/venv` is not importable within ~5 min, or the model
     download runs below ~300 MB/s, delete the pod and retry once, then fall back to Secure.
  2. Build the prebuilt image with the venv baked in (already a HANDOFF "Later" item). That takes the
     12 GB pip download off the critical path on every host.
  3. Log `/proc/loadavg` and the download speed in setup.log, so bad hosts are visible.
- **Evidence level:** measured on one host. It may well be bad luck. Community quality varies per machine.

### F2. A100 80GB PCIe: expected break-even vs H100 Community, cheaper than H100 Secure (estimate)
- **Mechanism:** The A100 has 312 bf16 dense TFLOPS and 1.94 TB/s (PCIe, 300 W). The H100 SXM has
  ~989 TFLOPS and 3.35 TB/s. LoRA SFT at pdb16 with gradient checkpointing is mostly GEMM-bound
  (forward + recompute + backward through frozen 14B weights). Public A100→H100 fine-tuning comparisons
  usually show 2–3× without FP8, not the 3.2× FLOPs ratio.
- **Expected:** 5.3–7.2 s/step → 65–88 min and **$1.28–1.74 per arm**, against $1.31 (H100 Community) or
  $1.94 (H100 Secure). Memory is the same 80 GB as the H100, so the pdb16 / accum 1 recipe fits unchanged.
  The numerics should be identical up to kernel nondeterminism: bf16, same kernels, no FP8 on either.
- **Side costs:** Evals (vLLM generation, packed probes) also slow down roughly 2×+ on the A100. Billed at
  44% of the H100 Community price, they come out roughly cost-neutral. Wall-clock time per arm roughly
  doubles to triples.
- **Risk to comparability:** Low. Same recipe, but arms in one comparison should still be trained on the
  same GPU type, because the bf16 reductions differ.

### F3. RTX PRO 6000 Blackwell (96 GB): only interesting if its extra memory allows turning checkpointing off (estimate / speculative)
- **Hardware:** ~1.8 TB/s bandwidth and roughly 2× less dense bf16 tensor throughput than the H100
  (datasheet-level; not verified on this workload).
- **Expected:** 4.1–5.3 s/step, which gives **$1.40–1.81 per arm** at $1.69/h. That is no better than the
  A100 PCIe.
- **Upside:** The 96 GB might fit pdb16 with `--gradient-checkpointing off`. That removes the recompute
  forward, typically saving ~25–30% of step time. If it fits, $/arm drops to ~$1.0–1.3, the only path
  here that clearly beats the H100 on dollars.
- **Caveats:** This needs a Blackwell-compatible torch, cu128+. The current image is torch 2.9.1 with
  cu128, so it should work. vLLM on sm_120 should be checked.
- **Risk to comparability:** Turning checkpointing off is numerically identical in principle (recompute
  gives the same values), so it is safe for a new experiment family.

- Same data and config as the H100 baseline (bench_train.sh config b): chatty Maya `train_Mch.jsonl`,
